# 时间、数据与目标契约

## 时间与日界线

时间采用 Unix epoch 毫秒存储，每条记录包含有序、不重叠的有效片段 `spans`。暂停是片段之间的空隙，不能把记录首尾相减当作有效时长。开始时间、结束时间与片段参与同步，不同步每秒 tick。

日期分组、日计划、目标和统计使用用户选择的日程时区，默认 `Asia/Shanghai`；设备系统时区不变。业务日从可选的 `settings.dayStartsAt`（00:00–06:00，缺省为零点）开始，凌晨在此之前的记录、完成和计划都属于前一天；只有 `dateKey`/`dayKey`/`dayStart` 知道日界线，课程与课表仍按日历日，详见 planning-goals.md。例如设备为 UTC-4、课程为 UTC+8 时，课程、任务日期和记录归日仍按设置的 UTC+8 计算。日界线由所选时区的日历计算，下一天按日历日期递增，不能固定加 86,400,000 毫秒；夏令时日可能为 23 或 25 小时。

主动时间记录不允许新增重叠。已保存记录仅占用有效片段；相接的半开区间允许并存，软删除不占用时间。未结束计时（包括暂停和旧冲突计时）从 `startedAt` 起持续保留时间，直到完成、取消或按截止自动结算，暂停空档仍不计入有效时长。打开计时前的补录允许在其起点恰好结束。

统一写入队列在最新快照上检查本次新增的占用，既有重叠不阻塞读取、改备注、裁剪、旧备份恢复或无关写入。同 ID 结束计时是把预留区间缩为实际片段。统计继续采用区间并集，兼容历史备份；自动采集和课程不是主动记录，独立保存并可以重叠。

## 同一计时记录

计时状态为 `null → running → paused → running → saved`。开始时锁定活动 ID 和性质；可同时保存任务关联 `taskId`、描述及相关标签。运行时长由已完成片段和当前运行片段计算，关闭窗口、锁屏和睡眠不会隐式暂停。

同步中未结束记录的 `timing.endAt=null`，`startAt`、`runningSince` 与 `spans` 表示起点和运行状态。结束时给同一个 ID 保存有效片段，不另外生成无关记录。UI 中的 `timelog.timer` 和 `records` 是这一模型的适配，见 sync.md。

可选 `plannedEndAt` 表示倒计时的计划截止时刻，没有该值则为正计时。新建倒计时至少一秒，运行片段始终截断到截止时刻；到期以相同 ID 保存，延迟唤醒或晚到请求不能延长记录。暂停冻结剩余时间，继续时按暂停持续时间顺延截止，暂停间隔不计入有效时长。`timerPresets` 保存在 `timelog.settings`，默认 `[5,30,45,60]`，可添加或删除；预设为 1 至 10080 的整数分钟，最多 30 项、去重。

`finishDueTimer` 是前台与中心共用的到期收尾规则。前台时钟和恢复前台时检查到期，ROG 的 `StateService` 在加载、读写及已安排的截止回调中再次检查；重复检查不会重复保存。写盘失败保留可恢复状态，不能宣称已经成功结束。离线 Android 后台 WebView 可能被冻结，恢复后按原截止保存，不承诺系统后台即时运行或通知。

调整开始时间不得晚于现在，也不得越过首段结束或计划结束；已有暂停间隔必须保留。“上一条记录末尾”只是填入开始时间的快捷方式。用户明确选择过去的完整起止范围时可保存为结束记录，未来结束时间进入倒计时。

下一个活动通过 `nextActivity` 在同一事务、同一时刻结束并记录当前项，再开始新活动。新活动有自己的 ID，旧活动最后边界与新活动开始边界一致。不能先写一次停止，再异步写一次开始而留下空档。

正常启动、暂停、结束、边界调整与 API 操作走统一 store / `StateService` 写入队列，在最新持久状态上校验。编辑表单以 `updatedAt` 或 revision 检查并发变化。设备时间倒退到运行起点前时拒绝暂停/保存，保留原计时。离线并发启动保留冲突计时，必须由用户处理，不自动丢弃或挑一个结束。

## 任务、活动与颜色

新档案不带活动。活动由用户新建、导入或同步。升级时只停用 ID、名称、颜色和性质仍与旧内置项完全一致、未手动排序、也没有被记录、计时、计时目标或清单引用的旧项。停用项保留身份，其他设备随后同步的历史仍能解析。

任务计时通过 `startTaskTimer` 带入任务 ID、标题和标签。优先用显式传入的活动或清单绑定。未绑定时只有一个活动则直接用它，有多个则选择，没有活动则先创建。失效绑定须在清单设置中更换。

记录/计时的可选 `taskId` 是单个完整任务实例引用，一个任务可以有多条记录。API 显式关联检查最新未删除任务，已完成任务可关联；历史/同步仍保留后来删除或旧导入的引用，不在加载时强制清除。`POST/PATCH /timelog/records` 支持建立/改绑，PATCH null 解绑、省略保留；纯关联只改变关联和记录 `updatedAt`，不改原片段与暂停间隔、活动/性质、描述、标签或当前计时。`timer/configure` 对运行/暂停计时只改 taskId，其余原 timer 完整快照保留，If-Match 拦截并发变更。任务关联不修改任务日期、完成状态、分组或手填实际分钟；API 2.1.0 详细错误/读回/AI Decision 围栏见 api.md。

清单与活动各自保存 `color`，待办和活动标签颜色分别保存在统一状态的 `tagColors.tasks`、`tagColors.records`。标签仍是任务/记录中的字符串数组；颜色元数据允许预先创建未使用标签，不为此新增另一套任务或记录实体。颜色参与校验、备份、增量保存和同步。

删除标签移除其颜色元数据与对应任务或记录/计时中的标签，内容本身保留。删除活动阻止新计时使用，并删除关联目标；若历史记录引用该活动，保留带 `deletedAt` 的身份供历史解析，否则可移除实体。正在主计时或冲突计时中使用的活动不能删除。UI 不提供归档/恢复入口；旧备份的 `archived` 字段仅作读取兼容。

## 目标

2026-11-02 用户要求删除积分系统：活动、记录、计时不再有 `pointsPerHour`，奖励与兑换实体一并删除。旧备份、旧同步文档读取时丢弃这些字段/实体，不报错也不保留。

目标分三种：自动计时（缺省 `kind`）、绑定待办标签（`kind: 'tasks'`）和手动勾选（`kind: 'manual'`，用户或 AI 按周期勾选），可带可选 `group` 分组名，判定统一走 `goalStatus`，详见 planning-goals.md。计时目标按关联活动的已保存有效区间并集计算，周期为每日或周一开始的自然周。`comparison` 为 `atLeast`（≥，旧目标默认）或 `atMost`（≤）。编辑器的“目标时间”接受 `9h`、`1h30m`、`90`（纯数字为分钟、表示至少）、`<2h`/`≤45分钟`（不超过）。**只有周期结束后才判定达成**（`goalStatus.met`，周期内为 null）：进行中的周期只显示进度、还需/还可/已超出，避免上限目标提前达成，也给忘停计时之类的错误记录留出修正时间。结果按当前记录实时推导，不保存结算快照；修正过去的记录会改变过去周期的结果。目标卡显示最近 7 个周期的达成情况，组标题统计上一个周期。

脚本和行为规则也共用目标模型与 `goalStatus`。行为规则的每日回顾随业务日结算并锁定，答案不产生达成结果。见 planning-goals.md。

## 保存与备份

时织使用一份经过校验的统一状态，任务、时间记录与课程都由同一保存通道拥有；`timelog/storage.ts` 是原模块导入/事务适配，不再拥有独立的 `open-timelog` IndexedDB 数据库。网页、Android 与 Electron 的具体保存方式见 storage.md 和 integration.md。完整加载、保存、导入都校验结构、数值、引用、ID 与片段顺序；损坏数据不能静默变为空状态。

记录删除标记与单调 `updatedAt` 用于历史、备份和同步，不等于产品重新提供回收站或归档功能。JSON 是无损备份；CSV 为分析导出，使用 UTF-8 BOM、公式前缀保护与 ISO 时间，不能无损恢复暂停片段。Markdown 导出按所选日程时区截断跨日片段。

兼容原模块格式：

```json
{ "format": "open-timelog", "version": 1, "exportedAt": "ISO-8601", "data": {} }
```

- 原模块备份合并按实体 ID 与 `updatedAt` 保留新版本，同版本不同内容拒绝整个合并。
- 本机或备份存在进行中计时时，原模块备份合并拒绝操作，避免静默丢失计时；完整恢复先导出本机安全备份，再明确替换。
- 完整时织状态导入（`/import`，AI 的读改写即用它）只合并历史：正在进行和冲突中的计时保持本机的，导入里的计时副本忽略。并发开始/停止由调用方的 revision（If-Match）拦截。2026-11-03 之前这里同样拒绝，导致计时进行中 AI 的任务与补录写入全部返回 500。
- 完整时织备份还包含任务清单映射、标签颜色与课程；原 Timelog 备份不包含这些模块。
- 旧 schema-1 备份可由新程序补默认值后读取，不表示旧程序能读取新增字段。中心与客户端需配套更新，见 sync.md。
- 原版 UpTimer 数据不属于此 schema，不能仅凭字段名猜测导入；既有迁移脚本和迁移记录是单独的显式流程。
