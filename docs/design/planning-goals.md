# 日界线、计划分组与目标

2026-11-03 用户确定的需求。修改日期归属、日计划分组、目标种类或给 AI 的对应接口前先读本文。

## 需求要点

- 一天从凌晨 4 点开始：00:00–04:00 的计时、完成和计划都算前一天。
- 日计划可以分组（如"午饭前""开会前""睡前"），分组属于某一天的计划，可带持续时间和截止时刻。分组只出现在待办的日计划里，不进入记录页或时间线。
- AI 早上排计划时直接创建分组并给出任务预计时长；定时任务、习惯统计不做主页展示。任务时长依据任务的 `estimatedMinutes` 与关联记录的实际用时，由模型自己分析。
- 目标可以分组；评估方式只有三种：自动（计时）、绑定待办、手动勾选。手动勾选可由 AI 直接代勾，不需要用户确认。
- 周期结束后再判定，规则沿用 `goalStatus`：进行中只显示进度。

## 日界线

`settings.dayStartsAt` 保存 `HH:mm`，范围 00:00–06:00，旧数据缺省为 `00:00`（不改变其他用户的行为），用户的数据设为 `04:00`。它和 `settings.timeZone` 一起参与设置的字段级合并与同步。

- 业务日期 `dateKey(at)`：把时刻转成所选时区的墙钟时间，减去 `dayStartsAt` 后取日期。必须用 Temporal 在墙钟上做减法，不能减固定毫秒，夏令时日照常是 23/25 小时。
- 业务日起点 `dayStart(key) = wallTime(key, dayStartsAt)`；`dayRange`、`weekRange`（周一 04:00 起）、目标、统计、时间线归日、Markdown 导出都由它派生。
- 只有这一组函数知道日界线。`timezone.ts` 的 `zoneDateKey` 保持日历日期，课程、课表、学期周次、ICS 与小部件继续使用日历日，不受日界线影响。
- 任务 `due` 仍是 `YYYY-MM-DD` 标签，含义变成"属于哪个业务日"。02:00 打开日计划看到的是前一天，"逾期"在 04:00 后才出现。重复任务的下一次日期也按业务日计算。
- 跨过 04:00 的计时按与各天的重叠部分分别计入，和现在跨零点的处理相同。

## 计划时段（数据名 planGroups）

2026-11-04 起界面统一称“时段”（用户：语义更明确），数据与 API 仍用 `planGroups`/`planGroupId`。日计划里每个时段是带主题蓝浅底、左侧色条和时钟图标的卡片，未选时段的任务放在最后的“未定时段”灰框。任务编辑面板选了日期就显示时段栏，末尾“＋”就地新建当天时段并自动选中；日计划标题旁的“＋ 时段”保留。

统一状态新增 `planGroups`，任务新增可选 `planGroupId`：

```ts
type PlanGroup = {
  id: string;
  date: string; // 业务日 YYYY-MM-DD
  title: string; // "午饭前"、"开会前"
  minutes: number | null; // 计划持续时间
  until: string | null; // 可选截止墙钟 HH:mm，如 "15:00"；早于日界线的时刻属于次日凌晨
  note: string;
  order: number;
  createdAt: string;
  updatedAt: string;
  deletedAt: string | null;
};
```

- 分组是日计划的一部分，不是第二套计划实体；任务仍由 `due` 决定属于哪天。任务带 `planGroupId` 时，`due` 必须等于分组 `date`。改任务日期、移入收集箱时同一事务清除 `planGroupId`。
- 删除分组只把其中任务变为未分组，不删除任务。分组排序与任务排序相互独立；组内顺序仍是任务原有 `order`。
- 日计划按分组 `order` 依次显示分组标题（标题、持续时间、截止时刻），未分组任务放在最后。组标题旁显示组内未完成任务的预计分钟合计，便于和持续时间对照。周计划、月历不显示时段（四象限已撤回）。
- 用户可以在日计划里新建、改名、删除时段，在 `TaskComposer` 里选择或用“＋”新建时段，长按拖动可以拖入其他时段。
- 同步按实体 ID/字段合并，和任务相同；校验时 `planGroupId` 必须引用同日、未删除的分组。

## 目标

`Goal` 增加 `group` 与 `kind`，旧目标读取时补 `group: null`、`kind: 'time'`：

| kind                | 需要的字段                                      | 周期结束后达成条件                                                    |
| ------------------- | ----------------------------------------------- | --------------------------------------------------------------------- |
| `time`（自动）      | `rules`、`minutes`、`comparison`、可选 `stages` | 满足任一规则的记录有效区间并集 ≥ / ≤ 目标                             |
| `tasks`（绑定待办） | `taskTag`                                       | 周期内 `due` 落在该周期、带此标签、未删除的任务全部完成，且至少有一件 |
| `manual`（手动）    | `checks`                                        | `checks[周期键].done === true`                                        |

- 计时目标的 `rules`（用户 2026-11-04 设计）：`{ activities: string[]; tags: string[]; excludeTags: string[] }[]`，至少一条，最多 20 条。记录满足任一规则即计入（同一时间只算一次）；规则内所选活动任选其一（空为任意活动），`tags` 必须全部带上，`excludeTags` 一个都不能带。“带 #a 或 #b”写成两条规则，因此不设任一/全部开关；只排除 #x 的规则表示所有不带 #x 的记录（含无标签）。旧数据的 `activityId` 读取时转成单条规则；API 仍接受 `activityId` 作为单活动简写，`rules` 整体替换。删除活动时去掉各规则里的它；只指定了它的规则删除，目标没有规则时随活动删除。编辑器每条规则一张卡片：活动块多选，标签块点一下“包含”、再点“排除”、第三下恢复，附规则摘要与“今天已匹配”。
- 计时目标可选 `stages`（分钟，升序，不含 `minutes`，最多 50 个）：“至少”目标阶段须小于目标，“不超过”目标须大于目标。编辑器写“8-15”（每单位一个）、“8, 9, 10”或“1h30m”；纯数字单位跟随目标（满 1 小时按小时）。`goalStatus` 返回 `reached/levels`（达到的阈值数/阶段数+1），`met` 仍只看最终目标。卡片显示“阶段 r/L · 下一阶段还需 …”与进度条刻度；热力图按 r/L 在灰与主题蓝之间均分。
- 活动与目标可选 `order`，由长按拖动写入并参与同步；没有 `order` 的旧目标在组内保持“每日在前、每周在后”。
- `group` 是可选的分组名字符串，目标页按分组显示，组内再显示日/周周期；不新建分组实体。
- `checks` 以周期键（日为 `YYYY-MM-DD`，周为该周一日期）记录 `{ done, by: 'user' | 'ai', at }`。进行中和刚结束的周期都可以勾选或撤销；AI 代勾时卡片显示一个小的 "AI" 标记，用户可直接改。
- 删除活动只删除引用它的 `time` 目标。删除标签不删除 `tasks` 目标，该目标在无匹配任务时显示"无任务"，周期结束后算未达成。
- 完成热力图在 统计 › 记录 › 目标（每日 8 周、每周 14 周），组标题“上期”统计沿用；三种目标共用 `goalStatus` 一个入口。

`tasks` 只采用"该标签当期任务全部完成"（用户 2026-11-03 确认），不提供"完成 N 件"的计数条件。

## AI 接口

- `GET /context` 增加 `dayStartsAt`、按业务日的 `today`、今天的 `planGroups`、全部未归档目标及当前与上一周期的 `goalStatus`（含 `met`、`progress`、`kind`）。
- 新增 `POST/PATCH/DELETE /plan-groups`；任务 PATCH 接受 `planGroupId`；`POST /goals/{id}/checks` 写入手动勾选（`by: 'ai'`），重复写同一周期幂等。全部走 `StateService` 写入队列与 `If-Match`。
- 模型只通过这些接口和既有任务接口改计划，不直接写 JSON。

## AI Decision 侧

- Node 的 `task_mutate` 增加分组和手动勾选动作，沿用 action_id 账本、未知响应只读核对。`dayweave.py` 的快照带上分组与目标状态。
- 早上规划创建当天分组并把任务放进去，预计时长依据 `habits.task_estimates`（扩大样本、附清单与标签，便于找同类任务）。按活动汇总的时长不再放入规划上下文。
- 新增用户定时任务 `settlement.yaml`：`30 4 * * *`，mode tracking，prompt 为"判定刚结束的业务日中手动目标"。自动和待办目标由 Dayweave 推导，AI 只补手动目标；结果在 08:00 规划中一句带过，不在凌晨发消息。
- 00:00 的规划不再承担"日终收尾"，改为睡前时段安排；日终收尾与次日预告移到结算之后的第一次规划。
- 控制器自己的业务日期（规划日期、核查日期）以 Dayweave `/context.today` 为准，不再单独按零点计算。

## 兼容与发布

新增字段要求 ROG 中心、三台桌面与两台 Android 同时升级，与以往 schema 扩展相同（见 sync.md）。顺序：Dayweave 发布并五端升级 → 在设置中把日界线改为 04:00 → 部署 AI Decision 的 Node/控制器改动与 `settlement.yaml`。旧客户端在升级前不能编辑新字段。
